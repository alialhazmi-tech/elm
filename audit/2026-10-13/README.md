## تشخيص viewer وحدود الاستنتاج

- أعادت العينة الحية 503 إلى `GET /api/viewer` عند **13:57:21**. في الثانية نفسها أعاد `GET /api/auth/get-session` الحالة **429** ورسالة `Too many requests. Please try again later.`، ثم تعافى الطلبان عند إعادة التحقق. كانت جميع القيم المرسلة اصطناعية، دون حساب أو رمز مستخدم حقيقي. لا يُثبت تزامن الطلبين سبب كل أخطاء السجل التاريخي.
- الكود المثبت من `@neondatabase/auth@0.5.0-beta` يستدعي `/get-session` حتى عند غياب `__Secure-neon-auth.session_token`. أثبت الاختبار بالـSDK الحقيقي وtransport معزول: الطلب بلا جلسة يتصل بالمزود ويتلقى 429؛ النسخة المصححة ترد زائرًا دون أي اتصال بالمزود أو القاعدة. هذا إزالة اعتماد غير لازم، وليس تحويل فشل جلسة موجودة إلى نجاح.
- [عينة Railway المنقحة](network/viewer-503-sample.json) توثق استمرار أخطاء viewer بعد النشر. لا تحتوي IP أو User-Agent أو كوكي أو بيانات حساب، وليست مقامًا لحساب معدل الأخطاء.
- لا تحتوي سجلات الإنتاج الحالية سبب الـcatch؛ ولم تعرض عينة `neon-auth` سجلًا مساعدًا. لذلك لا نجزم أن تحديد المعدل يفسر جميع 503، ولا أن تخزين المحررين سليم لكل المستخدمين.
- مع وجود كوكي العضو، يستمر SDK والتحقق الحي من `member_profiles.status`. التعليق يلغي الهوية. جلسة المحرر تُفحص بتوقيعها وانتهائها و`sessionVersion` والحالة والصلاحيات الحالية. لا تغيير لدور المستخدم أو MFA أو سياسة النشر.
- `loadActor({strict:true})` يميّز غياب إعداد التخزين عند جلسة محرر صالحة عن غياب الجلسة؛ يعيد viewer عنده 503. الاستدعاءات الأخرى تحافظ على سلوكها الافتراضي.
- استجابة viewer دائمًا `Cache-Control: private, no-store`، مع `X-Request-Id` UUID مولّد في الخادم. حدث `viewer-dependency-failure` يضم فقط `requestId, dependency, operation, status, code, durationMs`. العمليات تحدد كوكي/جلسة/تحديث تحقق/ملف عضو/جلسة محرر/ملف محرر/صلاحيات. رموز الأخطاء محددة بقائمة سماح؛ لا message أو stack أو SQL أو cause أو URL أو user ID أو بريد أو tokens في السجل الجديد.

اختبار `tests/viewer-route.test.mjs` يغطي الزائر، العضو، المحرر، انتهاء الجلسة، الجلسة الملغاة بالإصدار، الحساب المعلق، صلاحيات حية بدل الدور داخل الرمز، 429/401/403/5xx، فشل الشبكة والقاعدة وغياب الإعداد، ربط السجل بالاستجابة، وعدم تسريب بيانات. اختبار التوثيق الموجود يغطي أيضًا فشل التحديث الإجباري لحالة البريد، مع الحفاظ على الكاش للحالة الموثقة.

### إغلاق الإنتاج بعد الموافقة والنشر

1. فريق المنصة يسجل commit ووقت النشر، ويجرب زائرًا وعضو اختبار ومحرر اختبار وجلسة منتهية في بيئة معزولة ثم الإنتاج وفق إجراءات الفريق.
2. يقارن نافذتين متماثلتين (ساعة قبل/بعد، ثم 24 ساعة): عدد الطلبات و503 لمسار viewer، وسجلات `viewer-dependency-failure` حسب `operation/status/code`.
3. يربط أي فشل عبر `X-Request-Id` مع السجل، دون نسخ بيانات الجلسة. يجب ألا يصدر طلب مزود هوية لزائر بلا كوكي. وجود 429 لعضو فعلي أو خطأ قاعدة يبقي سببه مفتوحًا، ويُراجع حد مزود الهوية/اتصاله وفق تشخيصه؛ لا زيادة حدود ولا تغيير proxy بالحدس.
4. لا إغلاق شامل قبل دليل بيئة اختبار متصلة ومقارنة الإنتاج. الاختبارات الحالية محلية معزولة؛ لا وصول إلى حسابات اختبار حقيقية أو قاعدة العلم عبر اتصال Neon المتاح.

## www: الحافة والأصل وDNS

[التقرير](network/tls-http.json) يثبت: DNS العام لـwww وapex يعيد عناوين Cloudflare؛ شهادتهما من Google Trust Services WE1، صالحة من 4 سبتمبر إلى 3 ديسمبر 2026؛ curl تحقق الاسم والسلسلة بنجاح. `https://www.alelm.net/` يعيد 308 إلى `https://alelm.net/`، والداخلي `/health?audit=20261013&source=www` يحفظ المسار والاستعلام. اختبار المتابعة انتهى إلى 200 بتحويل واحد.

Railway يؤكد أن apex `VALID/PROPAGATED`، وwww `ISSUING/REQUIRES_UPDATE`، ويتوقع CNAME `www -> x7thax3u.up.railway.app`. سجل CNAME خلف Cloudflare قد يكون مخفيًا للعامة؛ لذلك لا نستنتج السجل الفعلي من A records. الاتصال المباشر إلى `69.46.46.93` (حل ذلك الهدف وقت الفحص) مع SNI الصحيح أعطى خطأ اسم شهادة، ولم يُستخدم `-k`.

**الإجراء الخارجي وصاحبه:** مسؤول منطقة Cloudflare/DNS مع مسؤول Railway يراجع السجل الفعلي، قاعدة تحويل www عند الحافة، مسار التحقق ACME وحالة شهادة www بالأصل، ويطابق القيم المطلوبة قبل التعديل. لا تعطيل proxy أو خفض TLS أو تغيير DNS عشوائيًا. تحويل الحافة العامل يفسر سلامة تجربة الزائر رغم أن شهادة أصل www لم تكتمل؛ إعدادات Cloudflare الداخلية نفسها لم تكن متاحة للقراءة.

## الأداء: الحقل منفصل عن المختبر

[التقرير المفصل والقياسات المكررة](performance/README.md) يتضمن الصفحات وظروف القياس ونتيجة كل تشغيل، لا الدرجة فقط. [PageSpeed/CrUX](https://pagespeed.web.dev/analysis/https-alelm-net/86wbdpyyms?form_factor=mobile) بتاريخ 13 أكتوبر، 14:31:48: **LCP p75 للجوال 2.1 ثانية، INP ‏108ms، CLS ‏0.01، واجتياز CWV** على مستوى `https://alelm.net` خلال آخر 28 يومًا. زر This URL غير متاح؛ لا نسب النتيجة لكل خبر أو لهذا PR غير المنشور. 81% من تحميلات الجوال في فئة LCP الجيدة، و7% في الضعيفة.

القياس المختبري الخارجي في التقرير نفسه أعطى LCP ‏8.9 ثانية وPerformance ‏63. له جهاز/شبكة محاكيان ونسخة Lighthouse مختلفة عن المقارنة المحلية، فلا تخلط أرقامه مع مقارنة A/B. اختُبرت طريقتان لتقليل preload للخطوط؛ تحسن LCP في بعض الحالات مع تراجع FCP في أخرى، لذلك أُلغي تعديل الخطوط من الكود النهائي. صورة LCP الحالية عالية الأولوية وWebP؛ لا إعادة تنفيذ لهذين التحسينين دون تشخيص.

بيئة `capacity-staging/elm-capacity` المتاحة مرتبطة بالمستودع السابق `sabq4org/elm`، وآخر نشر بتاريخ 22 سبتمبر فاشل، وأسماء متغيراتها لا تتضمن إعدادات هوية الأعضاء. ليست بيئة إثبات متصلة للفرع الحالي. تجهيز بيئة اختبار مماثلة للإنتاج ومراجعة موارد الطرف الثالث وCSS/JS المتأخرة هو الإجراء التالي قبل اعتماد تعديل أداء جديد.

## SEO وإمكانية إعادة التحقق

**تحديث بعد وصول Excel:** الرابط في `Sheet1!B7` أتاح تصدير الأوصاف الأصلي كاملًا (848 رابطًا). [أُعيد زحفه](seo-original/README.md) بين 15:56:19 و16:02:28: 847 صفحة 200 مباشرة وتحويل 308 واحد من 1658 إلى 1660، وصفر أوصاف وعناوين وcanonical مفقودة أو مكررة. انقطاع `RemoteDisconnected` واحد حُفظ في الجولة الأولى وتعافى عند إعادة طلب مستقلة موثقة. هذا يثبت حالة القائمة الأصلية وقت الفحص؛ لا يحدد الحالات الثماني المستقلة، لأن الرابط تصدير أوصاف لا قائمة عناوين. لم يتطلب الفحص تعديل كود التطبيق.

Sitemap احتوت **29,603** رابطًا؛ الأداة أخذت أول 60 رابطًا ثم نقاطًا موزعة على الأرشيف، مع إزالة التكرار: **159** رابطًا. الزحف من 14:03:24 إلى 14:05:43. القائمة والنتائج وJSON-LD وأمثلة التكرار/النقص (CSV بعناوين أعمدة فقط، لأن العدد صفر) موجودة في [seo](seo/). المطابقة تستخدم النصوص المستخرجة بعد فك HTML entities؛ هذه ليست مراجعة دلالية لتشابه العناوين. المفقود والمكرر يحسبان لصفحات 200 فقط، وعددها موثق.

[نتائج Google](seo/rich-results.json) منفصلة عن فحص JSON-LD المحلي. الرئيسية تحتوي `NewsMediaOrganization` و`WebSite` في HTML، بينما Google قال `No items detected` للنتائج المنسقة على الرئيسية. صفحة الخبر صالحة مع تحذير اختياري `author.url`؛ لا نضيف مؤلفًا أو رابط تعريف غير معتمد فقط لإزالة التحذير.

[فحص الجوال](seo/mobile-breadcrumbs.json) عند 390×844 تحقق من الخبر والقسم والسلسلة والوسم: لا overflow أفقي، والأسماء المرئية تطابق JSON-LD. كشف فحص Google أن الوسيط غير المربوط بصفحة في الوسوم غير صالح؛ الإصلاح يحافظ على URL وCanonical وSitemap ولا يتطلب تحويلات.

حماية أصل Railway هي سياسة **منع الوصول** (403)، وhealth استثناء محدود. لا نزعم أن noindex في استجابة محمية قرأه Google، ولا نعتمد على `Disallow: /` لإزالة مفهرس سابق. إذا ظهرت نتائج قديمة، يتولى مالك Search Console فحص URL والإزالة المناسبة مع إبقاء الأصل محميًا. [إرشادات noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing) تتطلب إتاحة الزحف لقراءة التعليمة؛ لا يُفتح الأصل لمجرد ذلك.

وفق [توثيق Article](https://developers.google.com/search/docs/appearance/structured-data/article)، Schema تساعد في فهم المحتوى، وليست شرطًا لازمًا لـTop Stories ولا ضمانًا للنتائج المنسقة. [توثيق Breadcrumb](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb) يسمح بإغفال item للعنصر الأخير، لا للوسيط.

## صلاحيات فريق SEO

لم يُعرف حساب الفريق بعد. قائمة مشاريع اتصال Neon المتاح لا تتضمن العلم؛ لا استنتاج بشأن وجود الحساب من ذلك. لم نقرأ أسرار Railway أو ننشر بيانات دخول. صلاحية `siteFullUser` في Search Console تخص خدمة Google، ولا تثبت وجود حساب لفريق SEO داخل تحرير العلم.

يتحقق **مسؤول الحسابات في لوحة تحرير العلم** من اسم/بريد الفريق وحالة active والدور وتجاوزات الصلاحيات. الحد اللازم لتحرير مواد مسندة هو `story.edit.own`؛ ولتحرير بيانات كل المقالات يلزم `story.edit.any` وفق النطاق المعتمد. الكود الحالي لا يملك صلاحية مستقلة تقصر التعديل على حقلي SEO: هاتان الصلاحيتان تسمحان بتعديل المادة نفسها. لذلك لا نمنح دور «مدير التحرير» أو Admin كاختصار. الخيار المقترح: دور مخصص بنطاق المواد المطلوب ودون users/roles/admin أو publish/archive، بعد تأكيد أن تعديل متن المادة مقبول؛ وإن لزم قصر حقلي SEO فقط فهو تطوير مستقل في الحارس وواجهة الحفظ. لا تُمنح صلاحيات قبل تحديد الحساب والنطاق.

## المخاطر والتراجع

الكوكي الغائبة تُحسم محليًا؛ أي كوكي جلسة موجودة تستمر عبر التحقق المعتاد. نقص إعداد DB مع جلسة محرر سيظهر الآن كـ503 تشخيصية بدل إظهار زائر. تجارب preload موثقة فقط وأُعيد `app/layout.tsx` إلى النسخة الأصلية؛ لا تغيير نهائي للخطوط أو أولوية صورة LCP. تغيير الوسم يحذف وسيطًا بلا صفحة ولا يغيّر أي URL.

التراجع: revert لالتزام/التزامات PR ثم إعادة نشر النسخة السابقة عبر مسار الفريق بعد الموافقة. لا migration ولا تعديل بيانات أو حسابات أو DNS يحتاج إلى تراجع. لا يوجد تعديل نهائي للخطوط يحتاج إلى نشر أو تراجع.

## الملفات والفحوص

- `app/api/viewer/route.ts` و`lib/session-diagnostics.ts`: ربط الطلب بالتشخيص الآمن مع بقاء استجابة التعذر 503.
- `lib/membership/session.ts` و`lib/tahrir/access.ts`: تمييز الزائر وحالة تعذر التحقق، مع بقاء فحص الحالة والصلاحيات الحية.
- `app/keywords/[keyword]/page.tsx`: توحيد المسار المرئي والمنظم الصالح للوسم.
- اختبارات viewer وkeyword breadcrumbs وتحديث fixture اختبار التوثيق؛ سكربتا قياس وزحف قابلان للإعادة؛ جميع أدلة هذه الجولة داخل هذا المجلد.
- **لا فرق نهائي في `app/layout.tsx`**؛ تجارب الخطوط موثقة ولم تُعتمد.

[سجل الفحوص](validation.json): `npm test` نجح محليًا؛ **476/476** اختبارًا، lint بلا أخطاء، typecheck، بناء production معزول وميزانية JS ناجحة. بقي تحذير img في BrandMark وتحذير staleTimes الموجودان سابقًا. اختبارات viewer/verification/breadcrumbs المركزة اجتازت 4/4 بعد تجهيز الأدلة. حالة CI واختبارات PostgreSQL تُسجل منفصلة؛ لا يساوي نجاح المحلي نجاح GitHub Actions.
