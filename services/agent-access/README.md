# خدمة وصول وكلاء «العلم» — خدمة مستقلة

هذه حزمة تشغيل منفصلة تدعم OAuth و`auth.md` وتسجيل الوكلاء. تدعم البحث وقراءة الأخبار العامة فقط. ليست موصولة بحسابات أعضاء الموقع أو التحرير، ولا تملك اتصالًا بقاعدة بيانات الموقع.

**النشر مستقل عن Next.js:** خدمة `agent-access` داخل مشروع Railway نفسه، بنطاق `agents.alelm.net` وقرص SQLite خاص بها، وbucket منفصل للنسخ المشفرة. دمج الملفات وحده لا يغيّر مسارات الموقع ولا تشغيله. النسخة العامة تقرأ الأخبار العامة عبر HTTPS فقط، ولا تُعطى متغيرات CMS أو Neon أو حسابات الموقع. DNSSEC يبقى دون تغيير.

التشغيل المحلي يستمع إلى loopback. وضع الإنتاج يتطلب `NODE_ENV=production` و`AGENT_DEPLOYMENT=railway` وHTTPS issuer مطابقًا ومجلدًا داخل قرص Railway مثبتًا وإعداد نسخ احتياطي مكتمل؛ يرفض التشغيل عند نقصها.

## التجربة المحلية

تحتاج Node.js 24.13 أو أحدث ضمن الإصدار 24. الحزمة لها lockfile خاص بها.

```sh
cd services/agent-access
npm ci --ignore-scripts
npm test
npm run test:browser # يتطلب Chrome مثبتًا؛ أو حدد CHROME_PATH
npm run demo
```

افتح `http://127.0.0.1:4318`. التجربة المحلية تنشئ قاعدة SQLite مؤقتة ومحتوى أخبار اصطناعيًا وحساب مالك اختبار منفصلًا. تعرض الطرفية **مسار ملف** بيانات الحساب فقط؛ الملف محلي بصلاحية `0600`. لا ترفعه أو تشاركه. أوقف التجربة بـCtrl+C واحذف المجلد المؤقت الذي طُبع مساره عند الانتهاء.

`npm start` يستخدم تخزينًا محليًا دائمًا في `data/agent-access.sqlite` ويقرأ واجهة الأخبار العامة عبر HTTPS عند طلب خبر. لا يتصل بقاعدة بيانات الموقع. للتجربة دون أي اتصال بالموقع استخدم `npm run demo`.

| المسار | الوظيفة |
|---|---|
| `/.well-known/oauth-authorization-server` | تعريف OAuth ومنح JWT bearer وclaim المنفذة فقط |
| `/.well-known/oauth-protected-resource/api` | تعريف مورد `/api` وصلاحية `news:read`؛ نسخة أيضًا عند المسار الأساسي |
| `/.well-known/jwks.json` | مفتاح التحقق العام فقط |
| `/auth.md` | خطوات التسجيل والقراءة والربط والإلغاء القابلة للتنفيذ |
| `POST /agent/identity` | تسجيل وكيل مجهول وإصدار assertion صالحة 24 ساعة |
| `POST /oauth2/token` | إصدار access token لمدة لا تتجاوز خمس دقائق |
| `GET /api/search` و`GET /api/articles/:id` | قراءة الواجهة العامة عبر مفتاح الخدمة |
| `POST /api/mcp` | MCP Streamable HTTP بأداتي `search_articles` و`read_article` |
| `/agent/identity/claim` و`/claim` | ربط اختياري بحساب مالك مستقل وموافقة بشرية |
| `POST /oauth2/revoke` | إلغاء مفتاح واحد؛ التسجيل يبقى فعالًا |
| `/owner/revoke` | إلغاء التسجيل وكل مفاتيحه بعد تحقق المالك |
| `/health` | فحص التشغيل والتخزين وحداثة آخر نسخة احتياطية |

القراءة تعمل قبل ربط المالك وبعده بالصلاحية نفسها. الربط ليس تسجيلًا بعضوية «العلم» ولا تأكيدًا لبريد إلكتروني؛ هو ربط بحساب مستقل أنشأه مشغّل هذه الخدمة. لا توجد رسائل بريد أو تسجيل مالك ذاتي أو موفرو هوية خارجيون.

## إدارة حساب المالك والإلغاء

أنشئ كلمة مرور عشوائية فريدة لا تقل عن 16 حرفًا. مررها من مدير كلمات المرور إلى stdin، وليس وسيطة في سطر الأوامر أو ملفًا داخل Git:

```sh
# تدفق stdin يأتي من مدير كلمات المرور؛ لا تكتب السر داخل هذا الأمر.
npm run admin -- create-owner owner@example.test
npm run admin -- revoke REGISTRATION_ID
```

أمر إنشاء الحساب يرفض الإدخال المباشر المرئي في الطرفية. لا يستبدل حسابًا موجودًا. المتغير `AGENT_DATA_FILE` يحدد ملف تخزين مستقلًا عند الحاجة؛ يجب أن يكون داخل مجلد خاص بهذه الخدمة. `AGENT_PORT` افتراضيًا 4318، و`AGENT_ISSUER` افتراضيًا عنوان loopback لذلك المنفذ. لا تُضبط أي متغيرات تخص Neon أو CMS.

## حدود الأمان والتوافق

- مفاتيح Ed25519 موقّعة بمكتبة `jose`، مع تحقق النوع والمصدر والجمهور والصلاحية والإصدار والانتهاء. المخزن يحتفظ بالمفتاح الخاص؛ يتطلب قرصًا خاصًا وحماية النسخ الاحتياطية.
- التسجيلات وclaims والإلغاء باقية في SQLite بعد إعادة التشغيل. يتم حفظ hashes لرموز claim والإلغاء، وكلمات مرور المالك باستخدام scrypt مع salt مستقل. لا تظهر كلمات المرور أو المفاتيح أو البريد أو cookies في سجل التطبيق.
- إلغاء التسجيل يبطل المفاتيح الحالية ويمنع إصدار غيرها. إلغاء access token وحده لا يلغي assertion. اكتمال الربط يغيّر إصدار التسجيل ويبطل جميع مفاتيحه السابقة.
- ربط المالك يتطلب كلمة مرور مستقلة وCSRF وOrigin مطابقًا ورمزًا من الوكيل. صلاحية محاولة الربط عشر دقائق وخمس محاولات رمز فقط. لا يمكن تغيير بريد المحاولة أو إعادة ضبط محاولاتها. بعد فشل دخول المالك عشر مرات يقفل الحساب 30 دقيقة.
- لا توسعة صلاحيات بعد الربط. لا توجد كتابة للمحتوى، ولا رفع ملفات، ولا وصول إلى `/api/viewer` أو `/tahrir` أو أي مسار خاص. قراءة المصدر محصورة في `https://alelm.net/api/content/v1/...`، دون تمرير credentials أو cookies أو السماح بتحويلات HTTP.
- الطلب 16 KiB، استجابة المصدر 2 MB، مهلة المصدر خمس ثوانٍ. خمس تسجيلات/دقيقة على مستوى الخدمة العامة كلها، 1000 تسجيل فعال، انتهاء وحذف بعد 24 ساعة؛ 30 قراءة للمصدر/دقيقة وأربع قراءات متزامنة على مستوى الخدمة كلها، مع حفظ حصة القراءة في SQLite عبر إعادة التشغيل. لا تُوثق عناوين IP في logs. لا نثق بترويسات forwarded لتجاوز الحدود.
- الوضع المدعوم نسخة واحدة وقرص SQLite دائم. الحصص محفوظة في SQLite، ولا نثق بـX-Forwarded-For أو CF-Connecting-IP: الطلبات العامة تشترك في حصة محافظة واحدة (90 طلبًا/دقيقة و5 تسجيلات/دقيقة). حدود التزامن تخص العملية. لا توسّع أفقيًا دون إعادة تصميم التخزين والحصص.
- OAuth هنا ملف JWT bearer وفق RFC 7523؛ امتداد claim خاص بمشروع auth.md. لا ندّعي OIDC أو authorization-code/PKCE أو federation أو تسجيل عملاء RFC 7591. عميل MCP يتصل بمفتاح تم إصداره من هذا التدفق؛ تدفق تسجيل الدخول الآلي في عملاء MCP الذين يشترطون authorization-code/PKCE ليس منفذًا.
- نتيجة claim تسلّم مرة واحدة؛ إن انقطع الاتصال وفُقد الرد بعد التسليم، يلزم تسجيل وكيل جديد. لا refresh tokens أو استرداد مالك عبر البريد في هذه المعاينة.
- يمكن للوكيل المجهول إنشاء تسجيل آخر ضمن الحدود؛ الإلغاء يمنع استخدام التسجيل الملغى، وليس حظر هوية إنترنت مجهولة نهائيًا.

## الاختبارات والتحقق

`npm test` يشغّل 29 اختبارًا محليًا ببيانات مصطنعة، بما فيها عميل MCP الرسمي، وتحقق التواقيع والصلاحيات والانتهاء، وتنافس الموافقة، وCSRF، وحدود التسجيل، واستمرار الإلغاء بعد إعادة التشغيل، ومنع تسريب credentials إلى المصدر. `npm run test:browser` يختبر الموافقة والإلغاء في Chrome فعلي ويؤكد وجود Origin وعدم إرسال رابط التحقق ضمن Referer؛ رمز التحقق موجود في fragment يُزال من شريط العنوان، فلا يُرسل في طلب GET إلى سجلات Railway. لا تحتاج أي أسرار أو صلاحيات إنتاج. CI مستقل على Node 24 يشغّل التثبيت وتدقيق التبعيات والاختبارات واختبار المتصفح، وتبقى بوابة جودة الموقع كما هي.

## تشغيل Railway واستعادته

إعداد الخدمة: الجذر `/services/agent-access`، Node 24، البناء `npm ci --omit=dev --ignore-scripts`، التشغيل `node src/server.mjs`، المنفذ 8080، نسخة واحدة، 0.5 GB ذاكرة و1 vCPU، قرص `/data` بسعة 512 MB، وفحص `/health`. لا يتغير إعداد خدمة `elm`.

- `AGENT_ISSUER=https://agents.alelm.net` و`AGENT_DATA_FILE=/data/agent-access.sqlite`، و`AGENT_SIGNING_GENERATION` قيمة إصدار ثابتة. تغيير الإصدار ثم إعادة النشر يلغي جميع التسجيلات ويولد مفتاح توقيع جديدًا؛ إعادة التشغيل بالقيمة نفسها تحافظ على المفتاح والإلغاءات.
- `AGENT_BACKUP_ENDPOINT/BUCKET/REGION/ACCESS_KEY_ID/SECRET_ACCESS_KEY` مراجع إلى bucket الخدمة `agent-access-backups` في Railway. `AGENT_BACKUP_PATH_STYLE=false` حسب إعداد Railway. لا تُنسخ بيانات اعتماد bucket الموقع.
- `AGENT_BACKUP_KEY` مفتاح AES-256 عشوائي من 32 بايت بصيغة hex؛ يُحفظ في متغير الخدمة ونسخة استعادة محلية محمية خارج Git. فقدانه يجعل النسخ غير قابلة للفك. لا تطبعه أو ترفعه في PR.
- نسخة مشفرة AES-256-GCM عند بدء التشغيل وكل ست ساعات، واحتفاظ سبعة أيام. تُعاد قراءة النسخة من التخزين الخارجي، ويُفحص التشفير وتكامل SQLite ومصدر الخدمة قبل اعتماد نجاحها. لا يصبح التشغيل جاهزًا قبل نجاح أول نسخة. `/health` يصبح 503 إذا مر أكثر من 12 ساعة دون نسخة ناجحة؛ Railway يفحصه أثناء النشر فقط، فلا يمثل ذلك نظام تنبيه مستمرًا.
- سجلات التطبيق: `backup_verified`, `backup_failed`, `service_ready` وأحداث التسجيل/الإلغاء مع معرف الطلب فقط. لا تسجل كلمات المرور أو tokens أو البريد. رابط الموافقة يستخدم fragment لمنع وصول رمزه إلى سجلات HTTP.
- HTTPS ينتهي عند حافة Railway؛ تُقبل طلبات التطبيق للنطاق المضبوط و`X-Forwarded-Proto: https` فقط. اسم مضيف فحص Railway مسموح فقط لـGET/HEAD `/health`، ولا يفتح أي API. النطاق الفرعي DNS-only؛ هذه الخدمة محمية بحدودها الخاصة وبحافة Railway، وليست خلف قواعد WAF الخاصة بالنطاق الأساسي.

### استعادة بعد فقد القرص

1. أوقف خدمة الوكلاء وحدها، واحتفظ بالقرص الحالي إن كان موجودًا. جهز قرصًا جديدًا فارغًا، بنفس issuer ومفتاح تشفير النسخ وبيانات bucket الخدمة.
2. حدد اسم ملف النسخة داخل prefix `agent-access/v1/` من bucket، واضبط `AGENT_RESTORE_OBJECT` عليه مرة واحدة. ابدأ النشر على القرص الفارغ؛ الاستعادة ترفض الكتابة فوق ملف قاعدة موجود أو استعادة نسخة لمصدر مختلف أو محتوى تالف.
3. الاستعادة تلغي كل التسجيلات القديمة وتحذف حسابات المالك القديمة ومحاولات الربط. هذا يمنع إحياء مفاتيح أو كلمات مرور أُلغيت بعد النسخة. يحتاج الوكلاء تسجيلًا جديدًا، ويعيد المشغّل إنشاء حسابات المالك عند الحاجة. لا تتأثر حسابات الموقع.
4. بعد تأكيد `backup_restored_all_registrations_revoked` و`backup_verified` و200 `/health`، احذف متغير `AGENT_RESTORE_OBJECT` مع تأجيل النشر. تركه سيوقف التشغيل التالي لأن القاعدة موجودة بالفعل.

تجربة الاستعادة الآلية تستخدم تخزينًا مصطنعًا وتختبر منع إحياء credentials ورفض التلاعب والكتابة فوق ملف موجود؛ التشغيل العام يتحقق من نسخة حقيقية عبر bucket بالقراءة العكسية. لا ندّعي اختبار تعطل كامل للقرص في الإنتاج.

### التراجع والحدود

التراجع الفوري: إيقاف خدمة `agent-access` وحدها، مع الاحتفاظ بقرصها وbucket ومفتاح النسخ. يمكن إعادة إصدار كود سابق متوافق مع المخزن؛ لا تنشر نسخة المعاينة القديمة كإنتاج. عند إلغاء الخدمة نهائيًا احذف فقط CNAME `agents` وTXT `_railway-verify.agents` اللذين أُنشئا لها. لا تغيّر سجلات الموقع أو DNSSEC. إيقاف الخدمة يوقف OAuth الخاص بها فقط؛ الأخبار والموقع وMCP العام السابق تظل مستقلة.

الخدمة لا تنفذ authorization-code/PKCE أو OIDC؛ عملاء MCP الذين يشترطون تسجيل دخول تفاعليًا يحتاجون عملاً منفصلًا. لم تُنشأ حسابات مالك عامة تلقائيًا؛ التسجيل المجهول والقراءة يعملان مباشرة. ربط المالك اختياري، يتطلب حسابًا مستقلًا ينشئه المشغّل عبر CLI داخل الخدمة. لا توجد صلاحية نشر أو إدارة الموقع.
