## تفعيل حماية الأصل بعد اعتماد النشر

الحد الأمني هو إثبات مرور الطلب عبر Cloudflare بسر طويل. Host وX-Forwarded-For وlocalhost وحدها ليست أدلة ثقة.

1. تحقق من أن جميع نطاقات القراء/iOS/Webhooks تمر عبر Cloudflare، خصوصًا عنوان Neon webhook؛ يجب أن يستخدم النطاق العام. تحقق من Healthcheck Path في Railway واضبطه على `/api/health` إن لم يكن مضبوطًا؛ وجود المسار في الكود لا يثبت تهيئة فحص المنصة.
2. أنشئ سرًا عشوائيًا منفصلًا (32 بايت أو أكثر) في مخزن أسرار التشغيل؛ لا تضفه إلى Git أو المتصفح أو السجلات.
3. أضف Request Header Transform Rule في Cloudflare للمضيفين `alelm.net` و`www.alelm.net` فقط، لجميع المسارات: **Set static** للرأس `x-alelm-origin-token` إلى السر، مع استبدال أي قيمة يرسلها العميل. لا تستخدم Response Header Rule ولا توسع المطابقة إلى أصل لا تملكه.
4. اضبط `ORIGIN_AUTH_SECRET` في Railway إلى القيمة نفسها. انشر الكود والحارس غير مفعل، ثم تحقق من سلامة الرئيسية والمقال والدخول والتطبيق وWebhook والمجدول.
5. اضبط `ORIGIN_AUTH_ENFORCE=1` عند جاهزية الطرفين. يتطلب ذلك دورة نشر/إعادة تشغيل معتمدة. غياب السر/قصره عند الإنفاذ يعيد 503؛ لا يفشل الحارس إلى السماح.
6. تحقق أن الأصل المباشر يرفض الرئيسية والمقال والدخول وAPI وملفات `_next/static` برد403، حتى مع Host/X-Forwarded-For/next-router-prefetch مزورة. يظل المرور العام سليمًا.
7. `/api/health` يسمح GET/HEAD فقط لحاجة الجاهزية ولا يعرض هوية أو محتوى. `/api/tahrir/tick` يسمح POST مع CRON_SECRET الصحيح فقط؛ لا مسار آخر يرث هذا الاستثناء. Neon webhook لا يستثنى: يمر عبر Cloudflare ويحتفظ بفحص توقيعه الخاص.
8. بعد توثيق الأصل يُستبدل x-forwarded-for بعنوان cf-connecting-ip الصحيح قبل وصوله إلى حدود الدخول والاستعادة، ويُحذف سر الأصل قبل التصيير. لا يرسل السر إلى القارئ.

الرجوع الطارئ: تعطيل `ORIGIN_AUTH_ENFORCE` يعيد الحالة السابقة ويفتح الأصل؛ يُسجل ذلك كتراجع أمني مؤقت. لا تحذف قاعدة Cloudflare أولًا أثناء الإنفاذ. تدوير السر يحتاج نافذة منسقة للطرفين.

مرجع إعداد الرأس: https://developers.cloudflare.com/rules/transform/request-header-modification/

## التحقق من CSP

افتح `/tahrir/login` و`/tahrir/recover` والتحرير بحساب محلي: nonce جديد لكل تحميل، لا unsafe-inline في script-src، عمل الثيم والنماذج وhydration. root bootstrap مسموح فقط بهاش النص المحدد، وThemeProvider يحمل nonce. الصفحات العامة تبقى قابلة لـISR. style-src لا يزال يسمح inline لدعم المحرر والتصاميم؛ فصل علاجه يحتاج اختبارًا مستقلًا.

## كلمات المرور وMFA

السياسة الجديدة تسري عند الإنشاء/التغيير/الاستعادة، ولا تغير التحقق من كلمات المرور القائمة ولا تلغي جلساتها دون إجراء صاحبها. قائمة الحظر محلية محدودة، وليست فحصًا شاملًا للتسريبات. إعداد `TAHRIR_MFA_ENFORCE` لم يُغيّر، ولا تدّعي الحزمة التحقق من تغطية حسابات الإنتاج. تفعيله يسبقه التأكد من إعداد مفتاح MFA وتوفر وسيلة تسجيل واسترداد للحسابات المعنية.

## قياس السعة

```bash
LOAD_ORIGIN=http://127.0.0.1:3138 LOAD_STAGES=1,5,10 LOAD_STAGE_SECONDS=10 LOAD_OUTPUT=tmp/capacity-local.json node scripts/audit/capacity.mjs
```

للبيئة التجريبية يحدد `LOAD_STAGING_HOST` المضيف الموافق عليه حرفيًا، مع `LOAD_ORIGIN=https://...`. يمكن تحديد `LOAD_PATHS` كمصفوفة JSON من path/type لصفحة المقال وواجهات GET المرتبطة. الأداة لا تتبع التحويلات ولا تستدعي POST. هذه دورة قراءة HTTP وليست محاكاة كاملة للمتصفح أو عدد قراء حقيقيين. تتوقف عند نسبة أخطاء تتجاوز10% بعد20 طلبًا وتفصل اعتراض Cloudflare عن خطأ الخادم. اربط نتائجها بذاكرة/CPU/اتصالات القاعدة/الكاش قبل تحديد السعة. لا يُقاس الإنتاج بهذه الأداة.

## حالة الإعدادات وخطة الإغلاق التشغيلي

فحص قراءة بتاريخ 13 سبتمبر 2026 لخدمة `elm` في مشروع Railway `Alelm`: البيئة الوحيدة هي `production`. قائمة المتغيرات لا تشمل `ORIGIN_AUTH_SECRET` أو `ORIGIN_AUTH_ENFORCE` أو `TAHRIR_MFA_KEY` أو `TAHRIR_MFA_ENFORCE`. لم تُعرض قيم الأسرار، ولم يُفحص حساب Cloudflare من الداخل؛ لا ادعاء بوجود قاعدة Transform مفعلة.

استعلام تجميعي على فرع Neon الإنتاجي: 23 موظفًا نشطًا، منهم 3 تشملهم قاعدة الإلزام الحالية بعد احتساب الصلاحيات والاستثناءات، وصفر حساب مفعّل عليه MFA. لم تُسحب أسماء أو كلمات مرور أو أسرار تحقق. هذه لقطة لحظة الفحص.

### حماية الأصل

في Cloudflare اختر Rules → Overview → Create rule → Request Header Transform Rule. استخدم المطابقة `http.host in {"alelm.net" "www.alelm.net"}` مع DNS من نوع Proxied، ثم Set static للرأس `x-alelm-origin-token` إلى سر مستقل من 32 بايت عشوائية ممثلة بـ64 خانة hex. الإعداد يخص رأس الطلب إلى الأصل ولا يظهر في رأس الاستجابة. في Railway أضف السر نفسه إلى `ORIGIN_AUTH_SECRET`؛ بعد التأكد من القاعدة اضبط `ORIGIN_AUTH_ENFORCE=1` وطبّق نشر المتغيرات.

معيار القبول: نجاح النطاق العام والرئيسية والمقال والدخول والأصول والتطبيق، ورفض الأصل المباشر403 للمسارات نفسها حتى مع الرؤوس المزورة. تحقق من `/api/health` ومن استمرار نبضات المجدول وWebhook عبر النطاق العام. لا تستدعِ نشرًا فعليًا للمجدول لمجرد الفحص. المجدول المضمّن يولّد سرًا داخليًا في `scripts/start-server.mjs` إذا لم يوجد `CRON_SECRET` صريح؛ العامل الخارجي وحده يحتاج قيمة ثابتة مطابقة.

هذه حماية على مستوى التطبيق: لا تخفي عنوان Railway ولا تمنع وصول اتصالات TCP أو تضمن منع استنزاف الموارد. الرجوع الطارئ هو تعطيل الإنفاذ قبل إزالة قاعدة Cloudflare مع تسجيل إعادة فتح الأصل.

### تغطية MFA

1. أضف `TAHRIR_MFA_KEY` عشوائيًا مستقلًا من64 خانة hex، واترك الإلزام معطّلًا أثناء الإعداد، ثم أعد النشر.
2. يربط أصحاب الحسابات الإدارية تطبيق TOTP من `/tahrir/security` ويؤكدون الرمز ويحفظون رموز الاسترداد خارج الحساب. لا تُشارك أسرار الربط في تقرير أو محادثة.
3. أعد قياس التغطية؛ المستهدف3/3 إن لم يتغير العدد، مع اختبار دخول واسترداد متفق عليه. لا تغيّر مفتاح التشفير بعد ربط الحسابات دون خطة ترحيل للأسرار المشفرة به.
4. اضبط `TAHRIR_MFA_ENFORCE=1` وأعد النشر، ثم تحقق من تحويل الإداري غير المسجل إلى إعداد الأمان ورفض API المحمية. لا يعمل الإلزام دون مفتاح صالح. السياسة الحالية تخص `*` و`users.manage` و`roles.manage`، ولا تشمل جميع الموظفين تلقائيًا.

### قياس السعة التجريبية

أنشئ بيئة staging بخدمة مماثلة لموارد ومنطقة وعدد نسخ الإنتاج وقاعدة Neon مستقلة. لا توجّهها إلى قاعدة الإنتاج، ولا تترك بريدًا أو جدولة نشر خارجية حقيقية مفعلة فيها؛ اضبط نطاق المشاركة ومنع الفهرسة. استخدم مضيف Railway تجريبيًا مختلفًا في `LOAD_STAGING_HOST`؛ الأداة ترفض `alelm.net` وكل نطاقاته الفرعية والأصل الإنتاجي المعروف حتى عند تحديده يدويًا.
